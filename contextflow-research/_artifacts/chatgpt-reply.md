DSH，你这次补充的真实 ChatGPT 登录态实验非常关键。尤其是 Session URL、SPA 导航、消息 DOM 标记、ProseMirror 输入框和剪贴板行为，已经把之前最大的技术不确定性缩小了很多。

不过，我对你提出的第一版方案有一个重要调整：

建议保留 Edge 扩展 + Python Core，但不要立即把“通过剪贴板读取完整回复”确立为正式通信协议。

因为目前的实测结果证明了网页交互机制可以工作，却还没有证明它适合长期承担 Coordinator 与 Core 之间的语义通信。

下面按照你提出的四个问题给出评审意见。

## 一、主要风险与遗漏

| 风险                  | 严重程度 | 建议                                   |
| ------------------- | ---- | ------------------------------------ |
| DOM 属性与 URL 结构变化    | 高    | 作为版本相关的观察结果，不当作稳定 API                |
| 程序化提取输出的条款限制        | 高    | 不把后台提取作为默认能力                         |
| 剪贴板污染与竞争            | 高    | 优先采用用户主动复制、主动交接                      |
| 回复完整性与任务完成判断        | 高    | 不把 `complete` 直接等同于 Coordinator 决策完成 |
| 多标签页、多 Session 路由错误 | 高    | 每次投递前明确目标 Session                    |
| Core 消息重复投递         | 中高   | 使用消息 ID、确认状态与去重                      |
| 网页内容诱导 Core 执行操作    | 高    | 所有网页内容均视为不可信输入                       |
| 浏览器扩展权限与本地服务安全      | 高    | 最小权限、来源验证、明确的操作授权                    |

### 1. 目前的 DOM 发现很有价值，但不能作为稳定接口契约

你发现的：

- `data-conversation-role`
- `data-talvt-turn-state`
- `data-chatgpt-selection-message-id`
- `data-chatgpt-selection-conversation-id`

可以成为实验适配器的观察依据。

但需要进一步验证这些标记是否在以下情况中仍然成立：

- 新会话、历史会话和 Project 会话
- 回复重新生成、编辑用户消息
- 包含工具调用和复杂组件的回复
- 长对话中消息被折叠或虚拟化
- 页面刷新、切换和网络中断

我建议采用一个简单原则：DOM 只能提供观察到的状态，不能直接成为 Core 的权威状态。

例如：

`data-talvt-turn-state="complete"` 可以意味着某个回合在页面上显示为完成，但不能直接证明整个任务已经满足要求，也不能证明 Coordinator 已经作出有效决策。

### 2. 剪贴板不应该成为隐形消息总线

你已经验证了通过 Ctrl+V 向 ProseMirror 输入框粘贴文本，以及通过复制按钮得到 Markdown。

这证明了一条可用的人工交互路径。

但剪贴板是操作系统级共享资源：

- 用户可能同时复制其他内容。
- 浏览器或其他程序可能覆盖剪贴板。
- 长文本可能包含敏感信息。
- 自动复制可能改变用户当前工作状态。
- 多个任务可能同时争用剪贴板。

因此，我建议第一版将剪贴板定位为用户主动触发的信息交接工具，而不是自动化传输层。

还有一个技术细节：既然已经能够观察到 ProseMirror 输入框，就值得研究 Edge 扩展是否能够通过受支持的浏览器编辑交互完成用户明确要求的填充操作，而不是必须修改系统剪贴板。不要依赖直接设置 `textContent` 或绕过编辑器事件系统。

### 3. 缺少一个明确的消息投递确认机制

当前方案中最容易出现的问题不是消息发送失败，而是：

消息看起来已经发送，但实际进入了错误 Session，或者重复发送。

建议 Core 中最小化保留以下信息：

```
message_id
target_session_ref
payload
created_at
delivery_status
```

其中 `delivery_status` 至少区分：

- `pending`：等待用户处理
- `prepared`：已填入输入框，尚未发送
- `submitted`：用户确认已发送
- `cancelled`：用户取消

注意：`submitted` 不应仅凭自动点击成功来判断，更不能等同于 ChatGPT 已处理消息。

第一版不需要完整消息队列，但需要避免把“输入框已填充”误认为“消息已送达”。

### 4. 最重要的遗漏：Coordinator 意图如何变成可信操作？

ContextFlow 的目标不仅是交换聊天文本，还需要把 Coordinator 的决策转化为 Core 操作。

例如：

“让 Codex 检查这个项目中的异常处理。”

这里存在两个不同的问题：

1. Coordinator 是否真的决定创建 Task？
2. Core 如何确认这条指令来自用户认可的 Coordinator，而不是某段引用文本、Worker 输出或恶意提示？

因此，不建议让 Core 直接扫描聊天内容并自动执行其中出现的命令。

第一版更适合采用：

Coordinator 提出操作 → Core 形成待确认操作 → 用户确认 → Worker 执行。

等官方工具集成与权限模型验证充分后，再考虑提升自主程度。

## 二、下一轮最值得做的三个实验

我建议按架构决策价值排序，而不是按实现难度排序。

实验 1：官方 MCP 集成能力验证

最高优先级

CF-EXP-002A · 架构决定性实验

验证 ChatGPT 是否能通过官方工具接口读取 ContextFlow Core 的 Task 状态、Worker 汇报，并在权限允许时创建 Task。

先检查实际账户是否具有自定义 MCP 连接权限；若没有，则使用独立 MCP 测试客户端验证服务端能力，不把它算作 ChatGPT 集成成功。

通过标准： 在原生 ChatGPT 会话中，能够调用自定义工具并得到测试结果。

实验 2：真实 Edge 多 Session 绑定与侧边栏体验

CF-EXP-002B · 产品体验验证

使用两个 Project、三个测试 Session，验证刷新、重命名、移动会话、多标签页和页面导航。

扩展侧边栏展示当前 Session、绑定状态、Core 连接状态和待处理消息。

通过标准： 不出现错误 Session 绑定；用户可以正常聊天；侧边栏能稳定显示 Core 状态。

实验 3：用户确认式消息交接闭环

CF-EXP-002C · 最小可用工作流

在本地模拟页面先验证消息准备、预览、确认、取消、重复处理及目标会话校验。

再通过真实 ChatGPT 的正常用户交互，验证用户手动复制 Worker 汇报并粘贴到目标 Session 的体验。

通过标准： 完成一次 Worker 汇报交接，不发生重复发送、目标混淆或剪贴板意外覆盖。

三个实验中，实验 1 最可能改变架构，实验 2 最能验证实际产品体验，实验 3 最接近第一版可用闭环。

## 三、是否存在更优的官方集成路径？

我重新核对了 OpenAI 当前的官方文档，结论是：

存在更适合语义协作的官方路径，但尚不存在能够完全替代原生会话双向读写的通用接口。

### 官方 MCP / Apps

官方最新文档确认：

- Business、Enterprise、Edu 支持完整自定义 MCP 工具，包括写入或修改操作，具体取决于工作区权限。
- Pro 可以连接具有读取、获取权限的自定义 MCP 服务，但不具备完整写操作支持。
- 本地 MCP 服务不能被 ChatGPT 直接连接，可以通过 Secure MCP Tunnel 或公网 HTTPS 端点提供服务。
- 自定义工具可以在原生 ChatGPT 会话中使用，但并不意味着外部程序可以主动向任意已有会话注入消息。

官方参考：[Connecting custom MCP servers in ChatGPT](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt?utm_source=chatgpt.com)

因此，我认为最值得长期研究的架构是：

ChatGPT 原生 Coordinator

自然讨论与决策

官方 MCP

任务操作 / 结果查询

Edge 扩展

Session / 界面状态

ContextFlow Core

状态管理、任务分配、执行历史

Codex CLI / Claude Code

Worker 执行

但这条路线存在一个关键限制：ChatGPT 何时主动调用工具？

如果 Worker 在用户没有发送新消息的情况下完成工作，普通会话不一定会自行发起下一次 MCP 调用。

所以 MCP 解决的是“Coordinator 如何访问 Core”，不一定解决“Core 如何唤醒 Coordinator”。

这两个能力应该在技术报告中独立记录。

另外，OpenAI 使用条款明确限制自动或程序化提取服务数据或输出。即使自动化操作通过技术实验，也不能仅凭用户确认就断言它符合条款。

## 四、“用户确认式剪贴板”的具体交互设计

我建议不要把它设计成一组自动化按钮，而是设计成一个非常轻量的消息交接面板。

ContextFlow

Core 已连接

当前绑定的 Coordinator Session

ContextFlow / 技术讨论

通过会话 URL 绑定 · 发送前再次核对

待交接的 Worker 汇报

Task #001

Codex 已完成 API 错误处理检查

发现 3 个需要处理的问题，已生成详细执行汇报。等待提交给 Coordinator 评估。

&#x20;复制汇报讨论交接流程

以上是交互示意。正式扩展中，“复制汇报”应由用户点击触发，内容来自本地 Core，而不是后台读取 ChatGPT 页面。

我建议第一版只实现四种交接状态：

| 状态  | 含义                  |
| --- | ------------------- |
| 待处理 | Core 已收到 Worker 汇报  |
| 已复制 | 用户点击复制，准备交给 ChatGPT |
| 已确认 | 用户确认已经完成交接          |
| 已取消 | 用户决定暂不交接            |

这里尤其要注意：已复制不等于已发送，已确认也不等于 ChatGPT 已经成功处理。

如果后续需要更严格的状态追踪，可以增加 `delivery_attempt_id` 和人工确认时间，而不必立即实现复杂的可靠消息协议。

### 具体交互建议

1. Worker 完成后，扩展侧边栏出现一条待处理汇报。
2. 用户点击汇报，查看摘要与完整内容。
3. 用户点击“复制汇报”，系统将格式化内容写入剪贴板。
4. 用户切换到绑定的 ChatGPT Session，手动粘贴并发送。
5. 用户回到侧边栏，确认已经完成交接。
6. Core 记录交接事实，但不擅自认为 Coordinator 已完成评价。

反向流程可以采用同样原则：用户通过 ChatGPT 原生复制功能取得需要交接的内容，再主动提交给 ContextFlow。

对于 Coordinator 的操作指令，Core 还应显示结构化预览，例如目标 Worker、工作目录、任务内容及权限要求，由用户确认后再执行。

## 五、给 DSH 的下一轮执行建议

我建议你将 CF-EXP-001 标记为技术探索完成、正式架构选型尚未完成。

下一轮不要继续扩大调研范围，而是集中在三个有明确验收标准的实验上。

尤其需要避免两种误判：

- 把网页可操作性误认为正式支持的接口能力。
- 把用户主动复制信息的便利性误认为自动化通信的可靠性。

当前可以初步确定的技术方向是：

Edge 扩展承担会话观察与工作台体验，Python Core 承担本地执行和状态管理；Coordinator 的语义通信优先研究官方 MCP，暂时保留人工确认式消息交接作为可用的过渡路径。

这条路线的好处是，即使后续发现某种网页自动化方式不稳定或不可采用，ContextFlow 的 Core、Worker 适配和工作台 UI 仍然具有独立价值，不必推倒重来。
