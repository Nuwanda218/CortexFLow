# 外部评审意见与下一轮计划（CF-EXP-001 → CF-EXP-002）

> 来源：2026-11-04 23:00，DSH 通过浏览器自动化把 CF-EXP-001 实测结果投递到用户真实 ChatGPT 会话「技术验证规划」，并取回其评审意见（原始回复见 `_artifacts/chatgpt-reply.md`，6042 字符）。
> 本文件是对该评审的结构化整理 + DSH 的判断，不改变用户对产品的最终决策权。

## 一、评审的核心调整

ChatGPT 的评审**认可** Edge 扩展 + Python Core 的方向，但提出一个关键调整：

> **不要立即把"通过剪贴板读取完整回复"确立为正式通信协议。**

理由：实测只证明"网页交互机制可以工作"，尚未证明它适合长期承担 Coordinator ↔ Core 的语义通信。剪贴板是 OS 级共享资源，存在污染、竞争、敏感信息、多任务争用等问题，应定位为**用户主动触发的信息交接工具**，而不是自动化传输层。

## 二、评审列出的主要风险（8 项）

| 风险 | 严重程度 | 建议 |
|---|---|---|
| DOM 属性与 URL 结构变化 | 高 | 作为版本相关的观察结果，不当作稳定 API |
| 程序化提取输出的条款限制 | 高 | 不把后台提取作为默认能力 |
| 剪贴板污染与竞争 | 高 | 优先用户主动复制、主动交接 |
| 回复完整性与任务完成判断 | 高 | 不把 `complete` 等同于 Coordinator 决策完成 |
| 多标签页、多 Session 路由错误 | 高 | 每次投递前明确目标 Session |
| Core 消息重复投递 | 中高 | 消息 ID + 确认状态 + 去重 |
| 网页内容诱导 Core 执行操作 | 高 | 所有网页内容视为不可信输入 |
| 扩展权限与本地服务安全 | 高 | 最小权限、来源验证、明确授权 |

## 三、评审建议的三个下一轮实验

### CF-EXP-002A · 官方 MCP 集成能力验证（最高优先级，架构决定性）

- **目标**：验证 ChatGPT 能否通过官方工具接口读取 Core 的 Task 状态 / Worker 汇报，并在权限允许时创建 Task。
- **前置**：先检查账户是否具有自定义 MCP 连接权限；若没有，用独立 MCP 测试客户端验证服务端能力，**不把它算作 ChatGPT 集成成功**。
- **通过标准**：在原生 ChatGPT 会话中调用自定义工具并得到测试结果。
- **DSH 补充判断**：用户账号为 **Plus**（侧边栏显示 `nuwandaair Plus`）。按官方文档，完整自定义 MCP 仅 Business/Enterprise/Edu；Pro 仅 read/fetch；Plus 未说明。→ **002A 在 Plus 账号下大概率不可执行**，应先向用户确认套餐/工作区，再决定是否投入。

### CF-EXP-002B · 真实 Edge 多 Session 绑定与侧边栏体验（产品体验验证）

- **目标**：两个 Project、三个测试 Session，验证刷新、重命名、移动会话、多标签页、页面导航；扩展侧边栏展示当前 Session、绑定状态、Core 连接状态、待处理消息。
- **通过标准**：不出现错误 Session 绑定；用户可正常聊天；侧边栏稳定显示 Core 状态。

### CF-EXP-002C · 用户确认式消息交接闭环（最小可用工作流）

- **目标**：本地模拟页先验证消息准备、预览、确认、取消、重复处理、目标会话校验；再在真实 ChatGPT 中验证用户手动复制 Worker 汇报并粘贴到目标 Session 的体验。
- **通过标准**：完成一次 Worker 汇报交接，不发生重复发送、目标混淆或剪贴板意外覆盖。

## 四、"用户确认式剪贴板"交互设计（评审建议）

第一版只实现四种交接状态：

| 状态 | 含义 |
|---|---|
| 待处理 | Core 已收到 Worker 汇报 |
| 已复制 | 用户点击复制，准备交给 ChatGPT |
| 已确认 | 用户确认已完成交接 |
| 已取消 | 用户决定暂不交接 |

**注意**：已复制 ≠ 已发送；已确认 ≠ ChatGPT 已成功处理。

交互流程：
1. Worker 完成后，扩展侧边栏出现待处理汇报；
2. 用户点击查看摘要与完整内容；
3. 用户点击"复制汇报"，系统把格式化内容写入剪贴板；
4. 用户切换到绑定的 ChatGPT Session，手动粘贴并发送；
5. 用户回到侧边栏确认交接完成；
6. Core 记录交接事实，但不认为 Coordinator 已完成评价。

## 五、评审对官方路径的判断

- 存在更适合语义协作的官方路径（MCP），但**不存在能完全替代原生会话双向读写的通用接口**。
- MCP 解决"Coordinator 如何访问 Core"，**不解决"Core 如何唤醒 Coordinator"**——这两个能力应在报告中独立记录。
- ToS 限制自动/程序化提取；即使技术实验通过，也不能仅凭用户确认断言合规。

## 六、DSH 对评审的回应与执行

**同意**评审的核心调整。DSH 补充两点：

1. **"不把剪贴板当自动总线"与实测一致**：扩展无法合成受信任的 Ctrl+V（除非 `chrome.debugger`），因此"用户主动粘贴"本来就是唯一低风险路径；把它明确为产品设计而非技术妥协，是正确的。
2. **"DOM 不是权威状态"应升级为架构原则**：Core 的状态机只接受"用户确认"或"官方工具返回"作为权威事件；DOM 观察只用于提示与校验。
