# ContextFlow C-04：ParseResult → Task / TaskDelivery

## 一、任务目标

实现阶段 C 的第一个最小功能：

**将已持久化的 ParseResult 转换为可追踪、可幂等重放的 Task 和初始 TaskDelivery。**

目标链路：

Message → ParseResult → Task + TaskDelivery

本阶段不执行 Agent，不实现 Dispatcher，不回传报告，不开发 Blackboard。

## 二、开发前检查

只阅读必要的现有代码与契约：

- 阶段 B 的 ParseResult、ParseJob、Message Store。
- 阶段 0 的 Task、TaskDelivery 契约。
- Agent Directory。
- 相关 SQLite 迁移机制。
- C-01 和 C-03 的交付位置与 Git 状态。

注意 C-01 可能位于独立 worktree，C-03 可能包含未跟踪文件。

不得覆盖、清理或擅自合并其他 Agent 的成果。

优先复用现有契约。发现冲突时采用最小兼容修改，不重新设计整个任务系统。

## 三、功能要求

### 1. 从 ParseResult 创建任务

只处理成功解析、已持久化且符合现有状态约束的结果。

每条有效指令创建：

- 一个独立 Task。
- 一个对应的初始 TaskDelivery。

保留：

- source_message_id。
- 解析结果身份或版本。
- 指令顺序。
- 目标 Agent。
- 指令正文。
- 创建时间。
- 必要的来源关联。

如果 ParseResult 包含多条指令，应创建多个 Task。

例如：

指令 1：Codex 修改代码。

指令 2：Claude Code 审查代码。

必须生成两个 Task，不能合并为一个执行。

指令顺序应被保存，但本阶段不实现依赖调度。

### 2. 幂等与冲突

以稳定的解析来源身份建立任务批次。

要求：

- 同一解析结果重复处理，返回已有 Task/Delivery。
- 不重复创建任务。
- 不重复创建初始 Delivery。
- 同一来源身份对应不同解析内容时，明确报冲突。
- 不静默覆盖已有任务。
- 不自行重新解析或重投递。

使用稳定的解析指纹。

指纹应基于规范化后的实际任务内容与目标，而不是易变的 UI 元数据。

同一批次的 Task、Delivery 和批次记录必须原子提交。

数据库事务失败不能留下部分任务。

### 3. 状态语义

Task 创建后处于待执行状态。

Delivery 创建后处于未投递状态。

不得将 ParseResult 成功视为 Task 完成。

不得将 Task 创建视为 Agent 已接受执行。

遵守：

**Execution finished ≠ Task accepted。**

如现有 TaskState、DeliveryState 不支持所需语义，优先映射到最接近的现有状态；只有无法准确表达时才进行最小契约扩展。

### 4. 未来协作预留

为后续 Agent 自主协作保留必要的来源关联：

- parent_task_id。
- requester_agent_id。
- origin_report_id。

首版允许为空。

如果现有契约已有等价字段，应复用而不是重复添加。

能够从 Task 反查：

- 原始 Message。
- ParseResult。
- Supervisor Endpoint。
- 指令序号。

不实现 Blackboard 或 Agent 间协作。

### 5. 最小触发入口

提供一个显式、可重复调用的入口，例如：

```
create_tasks_from_parse_result(message_id)
```

具体函数名可根据项目风格确定。

首版只支持显式触发，不自动消费全部 ParseResult。

不允许创建 Task 后自动执行 Agent。

## 四、测试要求

至少覆盖：

1. 单条指令创建 Task 和 Delivery。
2. 多条指令创建多个独立 Task。
3. 重复调用返回已有记录。
4. 同一来源内容冲突被拒绝。
5. 事务失败无部分写入。
6. 重启后任务仍可读取。
7. 来源身份和指令顺序可追溯。
8. 非成功解析结果不会创建任务。

使用隔离 SQLite 数据库。

不调用真实 Agent，不产生付费模型请求。

只运行与本阶段直接相关的测试和必要的轻量回归，不进行无边界的全仓库测试。

## 一、任务目标

在已验收的 C-04 基础上，实现最小任务投递与执行追踪能力。

目标链路：

Task + TaskDelivery → Dispatcher → Agent Adapter → ExecutionResult

本阶段只支持一个明确指定的 Agent Runtime，不实现多 Agent 自动调度。

**核心目标：可靠地启动一次 Agent 执行，并将执行身份、状态和结果关联回原始 TaskDelivery。**

## 二、开发前确认

检查：

- C-04 的 Task/Delivery Repository。
- C-03 的 Agent Runtime Interface。
- ExecutionRequest、ExecutionHandle、ExecutionSnapshot。
- ExecutionJournal。
- Agent Directory。
- 已有 TaskDelivery、TaskDispatcher 契约。

确认 C-03 正式 Adapter 代码已进入当前可用开发基线。

不得复制另一份 Agent Runtime，也不得修改 C-01 的绑定逻辑。

## 三、功能要求

### 1. Agent 运行绑定

建立最小可信配置：

AgentId → RuntimeKind + Workdir + ExecutionPolicy

至少包含：

- 目标 Runtime。
- 绝对工作目录。
- 会话策略。
- 权限或沙箱配置。
- 超时。
- 必要的并发限制。

运行配置由 Core 管理，不得由 Parser 输出的自然语言直接指定危险权限或任意工作目录。

首版固定：

- 一个 Agent。
- 一个明确工作目录。
- 新会话执行。
- 保守权限。
- 无自动重试。

### 2. ExecutionRequest 转换

从待投递 Delivery 生成 ExecutionRequest。

要求：

- instruction 来自 Task 的指令正文。
- caller_ref 使用稳定的 DeliveryId。
- runtime 来自可信配置。
- workdir 来自可信配置。
- session_policy 使用固定的新会话策略。

不得混淆：

- TaskId。
- DeliveryId。
- ExecutionId。
- Agent 原生 SessionId。

### 3. 投递状态与持久化

启动执行前，必须持久化投递意图或 sending 状态。

成功获得 ExecutionHandle 后，保存：

- TaskId。
- DeliveryId。
- ExecutionId。
- RuntimeKind。
- NativeSessionId（如果存在）。
- 当前执行状态。
- 必要的时间戳。

Core 应持久化 Task/Delivery 与 Execution 的关联。

C-03 的 ExecutionJournal 是执行侧记录，不应代替 Core 的任务关联记录。

不要建立两套互相竞争的权威执行状态。

### 4. 执行状态查询

通过统一 Adapter 接口获取执行状态。

至少支持：

- pending。
- running。
- finished。
- failed。
- cancelled。
- unknown。

状态必须来自可靠执行证据。

不得把进程退出直接视为业务任务完成。

不得把 Agent 自称完成视为 Task 已验收。

### 5. Unknown 与崩溃恢复

这是本阶段的关键可靠性要求。

如果 Core 在启动 Agent 前后崩溃：

- 必须保留投递意图。
- 不得自动启动第二次可能产生副作用的执行。
- 能查询已保存的执行身份。
- 能根据 Runtime Journal 和 Adapter 能力尝试对账。
- 无法确定结果时保留 unknown。

如果 Adapter 不支持跨进程恢复，应明确记录限制。

不要求本阶段解决所有 unknown，但不能错误地将 unknown 变成 failed、cancelled 或可安全重试。

### 6. 执行结果

执行结束后，持久化必要结果：

- 执行终态。
- 输出或结果引用。
- 错误信息。
- Usage（如果可获取）。
- NativeSessionId。
- 结果完整性。
- 副作用可能性。

不要将所有大型输出无上限写入单个数据库字段。

可以复用现有 ExecutionJournal 或使用文件产物引用。

### 7. 最小触发方式

提供显式触发入口：

```
dispatch_delivery(delivery_id)
```

具体名称可根据现有代码调整。

首版不自动扫描全部待执行任务。

不实现智能 Agent 选择。

不实现自动失败重试。

## 四、测试要求

优先使用 Fake Adapter 验证：

1. 待执行 Delivery 成功启动。
2. 正确构造 ExecutionRequest。
3. 正确保存 ExecutionHandle。
4. 重复触发不会启动第二次执行。
5. Adapter 明确失败时正确记录状态。
6. 启动过程中崩溃或结果不明时保留 unknown。
7. 执行状态可以更新和查询。
8. 终态与 Task 验收状态相互独立。
9. Runtime 配置缺失时拒绝投递。
10. 并发或重复调用不会绕过幂等保护。

增加一个使用真实 Adapter 的最小集成验证，但必须满足：

- 由用户明确授权。
- 使用隔离工作目录。
- 不修改真实项目文件。
- 不超出已确认的费用和权限边界。

未经授权时只使用 Fake Adapter，并明确报告真实调用未验证。

## 一、任务目标

在已验收的 C-04、C-05 基础上，完成 Agent 执行结果到原 Supervisor 的回传。

目标链路：

Supervisor 指令
→ ParseResult
→ Task
→ TaskDelivery
→ Agent Execution
→ AgentReport
→ Supervisor 审核

**核心目标：让 Supervisor 能够收到可追溯的 Agent 执行报告，并对任务作出审核决定。**

本阶段不实现 Agent 自主协作或 Blackboard。

## 二、开发前确认

检查：

- C-04 Task/Delivery 持久化。
- C-05 Execution 关联与结果读取。
- C-01 Supervisor Endpoint 与定向发送能力。
- 阶段 0 AgentReportEnvelope 契约。
- Message Store。
- Endpoint Registry。

确认：

- 能从 Task 找到原始 Message。
- 能从 Message 找到 Supervisor Endpoint。
- 能从 Delivery 找到 Execution。
- 能从 Execution 获取结果。
- 能通过 C-01 的已有能力向正确 Supervisor Session 发送消息。

不得另建第二套 Supervisor 身份系统。

## 三、功能要求

### 1. AgentReport 生成

从执行结果生成 AgentReportEnvelope。

至少包含：

- TaskId。
- DeliveryId。
- ExecutionId。
- AgentId。
- 执行终态。
- Agent 原始报告或输出。
- 错误与诊断信息。
- 可用的执行产物引用。
- 必要的时间戳。

必须区分：

- Agent 原始输出。
- Adapter 记录的执行事实。
- Supervisor 审核决定。

不得因为 Agent 报告“任务完成”就将 Task 自动标记为 accepted。

### 2. 报告持久化

在回传之前持久化报告及其关联身份。

要求：

- 同一次 Execution 不重复生成相同报告。
- 重复处理返回已有报告。
- 报告能反查 Task、Delivery、Execution。
- 报告正文和执行元数据可区分。
- 报告生成失败不能破坏已有执行记录。

复用现有 AgentReportEnvelope 和 Message Store 契约。

如果需要额外的报告投递状态，只增加最小必要结构。

### 3. Supervisor 定向回传

使用原始 Task 的来源信息定位 Supervisor Endpoint。

不得使用：

- 浏览器当前活动标签页。
- 当前最近打开的 ChatGPT 对话。
- 项目名称。
- 对话显示名称。

作为可信路由依据。

必须基于已绑定的 Endpoint 和原始 Session 身份进行定向发送。

发送失败时：

- 保留待发送报告。
- 记录失败或 unknown。
- 不丢失报告。
- 不盲目重复发送可能已经成功的消息。

如果 C-01 当前只有向 Core 提交消息的能力，而没有经过验证的 Core → ChatGPT 定向回传能力，应先明确缺口，复用现有 Bridge/Extension 能力做最小接线，不得假定该链路已经可用。

### 4. 回传与审核状态分离

至少区分：

- 报告已生成。
- 报告待发送。
- 报告发送中。
- 报告已确认送达。
- 报告送达状态未知。
- 报告等待审核。
- 审核通过。
- 审核要求返工。
- 审核拒绝。

以上是语义要求，不要求机械地为每一项创建独立数据库枚举。

根据已有契约采用最小状态模型。

特别注意：

**报告送达不代表 Supervisor 已审核。**

**Supervisor 审核通过不必然代表用户已最终验收。**

### 5. Supervisor 审核决定

提供最小的结构化审核入口。

至少支持：

- accept：审核通过。
- request_changes：要求修改。
- reject：拒绝成果。

审核决定必须关联具体 Task 和报告。

需要验证决定来源属于原任务授权的 Supervisor。

首版允许显式提交审核决定，不要求自动从所有自然语言回复中推断审核结果。

审核通过后才允许更新相应的审核状态。

对于需要用户最终确认的任务，应保留用户验收状态，不自动代替用户作出决定。

### 6. 返工处理

当 Supervisor 要求修改时：

- 保留原始执行记录。
- 保留原始报告。
- 保留审核意见。
- 不覆盖历史结果。
- 不自动重新启动 Agent。

本阶段只需要记录返工决定和后续执行所需的关联信息。

真正的重新投递可以作为后续阶段实现。

### 7. 最小端到端验证

使用一个明确指定的 Supervisor Session、一个 Task 和一个 Agent。

验证：

1. Task 可以找到来源 Supervisor。
2. ExecutionResult 可以生成报告。
3. 报告先持久化再发送。
4. 报告不会路由到错误 Session。
5. 重复回传不会无意产生第二份报告。
6. Supervisor 能够收到并识别 TaskId。
7. Supervisor 能够提交结构化审核决定。
8. 审核结果被持久化。
9. Agent Execution finished 不会自动触发 Task accepted。
10. 用户最终验收权未被隐式替代。

优先使用 Fake Adapter 和隔离环境。

真实 ChatGPT 浏览器回传需要明确授权和可控测试会话。

如不能安全验证真实回传，必须说明仅完成模拟闭环，不得声称真实端到端已打通。
