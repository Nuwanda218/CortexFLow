# ContextFlow 产品与界面设计文档

**版本：v0.1｜初步设计稿**
**阶段：需求设计**
**设计原则：简洁、高效、可控、低认知负载**

## 1. 产品概述

### 1.1 产品定位

ContextFlow 是一个以 ChatGPT 网页端为主要智能交互入口，通过统一消息流、协作流程图和消息泳道图，帮助用户观察并控制多个独立 Agent 协作过程的工作台。

它允许用户在统一界面中与多个 AI 工具协作，并通过一个具备全局上下文的智能调度者，共同规划、调整和执行工作流程。

ContextFlow 不以替代现有 AI 工具为目标，而是希望充分利用不同工具已有的能力，降低用户在跨工具协作中的协调成本。

### 1.2 核心理念

> **让工具承担协调，让人专注思考。**

产品追求的不是最大化 Agent 数量，也不是最大化自动化程度，而是：

**减少用户在消息转发、窗口切换、状态追踪和任务协调上的认知负担，同时保持用户对整体工作过程的理解与控制。**

### 1.3 核心使用模式

用户在统一群聊中表达需求。

全局调度 Agent 结合当前工作目标、历史消息、任务状态和其他 Agent 的能力，提出下一步工作建议。

用户可以审阅、修改或拒绝建议。

确认后，ContextFlow 将任务交给相应 Agent，并持续更新协作流程图、消息泳道图和节点执行状态。

整个过程形成：

**自然交流 → 智能建议 → 用户确认 → Agent 执行 → 结果汇总 → 下一轮协作。**

## 2. 页面整体布局

### 2.1 三栏式布局

主界面由三个可独立折叠的区域组成。

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ContextFlow       工作空间：刷题网站       Agent 状态       设置          │
├───────────────────┬──────────────────────────────────┬───────────────────┤
│                   │                                  │                   │
│   协作群聊        │           协作可视化             │     节点详情      │
│                   │                                  │                   │
│  用户             │   [流程图]  [消息泳道]           │  节点名称         │
│  ChatGPT          │                                  │  执行 Agent       │
│  Codex            │                                  │  当前状态         │
│  Claude Code      │          可交互画布              │                   │
│                   │                                  │  输入信息         │
│  ─────────────    │                                  │  输出结果         │
│                   │                                  │                   │
│  全局调度建议     │                                  │  执行日志         │
│                   │                                  │                   │
│                   │                                  │  关联消息         │
│                   │                                  │                   │
│  ─────────────    │                                  │                   │
│                   │                                  │                   │
│  输入消息……       │                                  │                   │
│  [发送]           │                                  │                   │
├───────────────────┴──────────────────────────────────┴───────────────────┤
│ 当前工作状态：2 个任务完成｜1 个任务运行｜1 个任务等待确认               │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.2 布局行为

三栏默认同时显示，但用户可以自由调整宽度。

| 区域             | 默认行为               | 折叠后                 |
| ---------------- | ---------------------- | ---------------------- |
| 左栏：协作群聊   | 显示完整消息流和输入框 | 保留展开入口           |
| 中栏：协作可视化 | 显示流程图或消息泳道图 | 保留视图入口           |
| 右栏：节点详情   | 显示当前选中节点的信息 | 完全收起，释放画布空间 |

**中栏是主要工作区域，应该获得最多的可用空间。**

当右栏关闭时，画布自动扩展。

当用户希望专注对话时，可以收起中栏和右栏，使左栏扩展为主要区域。

布局状态应在工作空间内保留，避免每次打开都需要重新调整。

## 3. 左栏：多 Agent 协作群聊

### 3.1 设计目标

左栏采用类似即时通信群聊的形式。

用户、全局调度 Agent 和其他执行 Agent 都可以作为独立主体出现。

**用户始终只需要面对一个主要输入框。**

不需要为了与不同 Agent 交互而频繁切换窗口。

### 3.2 消息展示

参考你提供的第二张图片，使用清晰的多主体消息样式。

设计规则：

- 用户消息靠右显示。
- Agent 消息靠左显示。
- 不同 Agent 使用不同头像和名称。
- 同一 Agent 的连续消息可以适当合并。
- 时间信息弱化展示。
- 消息正文保持清晰，不使用过多装饰。
- 长消息支持折叠和展开。

不同 Agent 的身份应当容易辨认，但不依赖大量颜色。

### 3.3 消息类型

群聊中需要区分以下消息：

| 类型            | 示例                    | 展示方式       |
| --------------- | ----------------------- | -------------- |
| 用户消息        | 我想了解项目整体架构    | 普通聊天气泡   |
| 调度 Agent 回复 | 建议先让 Codex 扫描源码 | 普通消息       |
| 调度建议        | 建议创建两个任务        | 可操作卡片     |
| Agent 执行结果  | Codex 已完成项目扫描    | 结果摘要卡片   |
| 系统事件        | 任务 T3 已启动          | 轻量状态提示   |
| 人工确认        | 用户批准执行任务 T3     | 简洁确认记录   |
| 异常通知        | Codex 执行失败          | 明确的错误提示 |

这里需要特别明确：

**执行 Agent 的全部终端输出不应默认进入群聊。**

群聊只显示必要的结果、摘要和关键事件。

详细执行过程放在右栏查看。

### 3.4 统一输入框

输入框默认面向全局调度 Agent。

用户可以自然表达需求，例如：

「我想进一步了解这个项目的数据库设计。」

调度 Agent 可以据此提出任务建议。

同时支持用户显式指定工具，例如：

「@Codex 帮我查看数据库表结构。」

第一版需要支持两种操作：

**自然调度：** 用户表达目标，由调度 Agent 生成建议。

**直接指派：** 用户明确指定目标 Agent，直接创建待确认任务。

两种模式不需要设计成完全独立的聊天界面。

### 3.5 调度建议卡片

当调度 Agent 提出行动方案时，在群聊中显示可操作卡片。

例如：

```
┌──────────────────────────────────────┐
│ 调度建议                             │
│                                      │
│ 任务：分析数据库设计                 │
│ 执行者：Codex                        │
│ 模式：只读                           │
│                                      │
│ 预期结果：                           │
│ 数据表关系及主要设计说明             │
│                                      │
│ [确认执行] [修改] [拒绝]             │
└──────────────────────────────────────┘
```

用户确认后，对应任务进入正式执行流程。

## 4. 中栏：协作可视化

中栏是 ContextFlow 最具辨识度的部分。

它需要提供两个主要视图：

**流程图视图**和**消息泳道视图**。

两个视图共享同一份工作状态，但表达不同的信息。

### 4.1 视图一：协作流程图

#### 目标

展示一项工作如何被拆分、分配、执行和完成。

用户可以同时看到：

- 已经完成的工作；
- 正在执行的工作；
- 尚未开始的工作；
- 等待确认的计划；
- 不同任务之间的依赖关系。

#### 节点设计

每个节点代表一个具体工作步骤，而不是一个固定 Agent。

节点至少显示：

| 字段     | 内容                           |
| -------- | ------------------------------ |
| 节点编号 | T01、T02 等                    |
| 执行主体 | 用户、ChatGPT、Codex 等        |
| 任务名称 | 例如「扫描项目结构」           |
| 当前状态 | 待确认、等待、运行、完成、失败 |
| 简短摘要 | 任务的主要内容                 |

点击节点后，右栏展示详细信息。

#### 连线设计

连线需要表达任务之间的关系。

第一版优先支持：

- **顺序依赖：** 任务 B 等待任务 A 完成。
- **并行分支：** 两个任务可以同时执行。
- **结果汇合：** 多个任务的结果共同输入后续任务。

不建议第一版就加入复杂的循环控制、条件表达式和自动执行脚本。

#### 计划与历史共存

这是我们之前确定的 C 方案。

流程图既展示已经发生的协作，也展示未来计划。

状态需要有清晰区别：

| 状态     | 视觉表达               |
| -------- | ---------------------- |
| 待确认   | 虚线边框               |
| 等待执行 | 普通边框、弱化内容     |
| 正在执行 | 强调边框和轻量动态状态 |
| 已完成   | 完成标识               |
| 执行失败 | 错误标识               |
| 已取消   | 弱化或划线             |

不需要复杂动画。

用户能够快速识别状态即可。

### 4.2 视图二：消息泳道图

#### 目标

展示不同 Agent 之间实际发生的消息传递。

它回答的问题与流程图不同。

流程图关注：

**这项工作是怎样组织和推进的？**

消息泳道图关注：

**谁在什么时候向谁传递了什么信息？**

#### 基本布局

每个参与者拥有一条泳道。

```
时间 ↓

    用户          ChatGPT          Codex         Claude Code
     │               │               │                │
     ●──────────────►●               │                │
     │   提出需求    │               │                │
     │               │               │                │
     │◄──────────────●               │                │
     │   调度建议    │               │                │
     │               │               │                │
     ●───────────────┼──────────────►●                │
     │   确认任务    │               │                │
     │               │               │                │
     │               ●◄──────────────●                │
     │               │   分析结果    │                │
     │               │               │                │
     │               ●────────────────────────────────►●
     │               │        请求审查                │
     │               │               │                │
     ▼               ▼               ▼                ▼
```

#### 两种信息密度

你特别提出了「缩略图」与「查看详情」的需求，我认为应该正式写入设计。

**概览模式：**

- 消息显示为简短标签或节点；
- 连线表达消息方向；
- 重点展示时间顺序和协作关系；
- 适合快速掌握全局。

**详细模式：**

- 点击消息节点展开内容；
- 显示消息来源、目标、时间和摘要；
- 可以查看完整消息；
- 可以跳转到关联任务。

详细信息优先在右栏展示，避免直接在泳道图中展开大量文本。

### 4.3 两种视图的关系

**流程图展示任务关系，泳道图展示通信历史。**

它们不应该各自维护独立的数据。

例如：

流程图中的 T03「Codex 分析数据库」，可能对应泳道图中的多条消息：

- 调度 Agent 提交任务；
- Codex 开始执行；
- Codex 返回阶段性结果；
- Codex 完成任务；
- 调度 Agent 接收结果。

用户点击其中任意消息，都可以找到关联的 T03 任务。

反过来，点击 T03，也可以查看它对应的消息记录。

## 5. 右栏：节点详情

### 5.1 设计目标

右栏负责展示当前选中对象的详细信息。

它可以显示任务节点，也可以显示消息事件。

默认不需要展示所有内容，只呈现与当前选择相关的信息。

### 5.2 任务节点详情

建议包含：

**基础信息**

- 节点编号；
- 任务名称；
- 执行 Agent；
- 当前状态；
- 创建时间与执行时间。

**任务内容**

- 原始任务描述；
- 输入上下文；
- 预期输出；
- 关联的前置任务。

**执行信息**

- 执行状态；
- 关键进展；
- 错误信息；
- 运行日志。

**执行结果**

- 结果摘要；
- 完整输出；
- 产生的文件或其他成果；
- 后续任务关联。

### 5.3 消息节点详情

从泳道图点击消息时，右栏切换为消息详情。

包括：

- 发送主体；
- 接收主体；
- 发送时间；
- 消息类型；
- 消息正文；
- 关联任务。

### 5.4 信息折叠

右栏应当默认展示最重要的信息。

例如，任务完成后，优先显示结果摘要。

用户需要时再展开完整日志。

**不要让大量调试信息长期占据用户视线。**

## 6. 全局调度 Agent

### 6.1 定位

全局调度 Agent 是用户的主要 AI 协作者。

它负责理解用户目标、掌握整体工作进展，并提出下一步行动建议。

它可以由 ChatGPT 网页端承担，但产品设计不应将这一角色永久绑定到某个具体工具。

### 6.2 基本能力

第一版需要具备：

1. 理解用户在主群聊中提出的需求。
2. 获取当前任务及其执行状态。
3. 了解可用 Agent 的能力。
4. 根据已有结果提出下一步建议。
5. 生成待确认的工作节点。
6. 在任务完成或失败后更新建议。

### 6.3 人工控制

第一版所有新任务默认需要用户确认。

用户可以：

- 接受建议；
- 修改任务内容；
- 修改执行者；
- 拒绝建议；
- 暂停或取消任务。

**全局调度 Agent 是协作者，不是不可干预的控制中心。**

### 6.4 调度建议与自然对话的关系

保留你之前提出的设计：

ChatGPT 可以继续进行正常的自然语言交流。

当系统需要识别行动建议时，再通过独立的结构化分析步骤生成任务草案。

但不能仅凭普通对话中出现的命令式文字就自动执行操作。

## 7. 工作空间与上下文

### 7.1 工作空间

ContextFlow 以工作空间组织不同项目。

例如：

- 刷题网站阅读；
- ContextFlow 开发；
- 课程学习；
- 其他研究任务。

每个工作空间拥有独立的：

- 主要目标；
- 协作消息；
- 任务流程；
- Agent 会话关联；
- 工作成果；
- 关键决策。

### 7.2 上下文原则

ContextFlow 不要求所有 Agent 共享完整历史对话。

它应当能够区分：

**原始消息、任务信息、执行结果、用户确认的结论。**

只有与当前任务相关的信息才需要传递给目标 Agent。

同时保留来源信息，避免不同 Agent 的推测被误认为已验证事实。

## 8. 视觉设计规范

### 8.1 整体风格

参考 Codex 桌面版的简洁风格。

关键词：

**克制、清晰、紧凑、轻量、专业。**

### 8.2 基本原则

| 元素   | 设计原则                       |
| ------ | ------------------------------ |
| 背景   | 以浅色或深色中性色为主         |
| 强调色 | 仅用于选中、执行状态和关键操作 |
| 边框   | 细线、低对比度                 |
| 圆角   | 适度使用，保持统一             |
| 阴影   | 非必要不使用                   |
| 动画   | 仅用于状态反馈                 |
| 图标   | 优先采用一致的线性图标         |
| 字体   | 保证中文、英文及代码清晰可读   |
| 留白   | 以提高阅读效率为目的           |
| 装饰   | 不添加没有功能意义的视觉元素   |

### 8.3 交互要求

- 所有重要操作应有明确反馈。
- 正在运行的任务容易识别。
- 重要错误不能被隐藏。
- 详细日志可以按需展开。
- 不应频繁弹出打断用户的提示。
- 画布支持缩放、平移与适应窗口。
- 三栏宽度可调整。
- 用户应能随时回到主群聊。

## 10. 验收场景

第一版应当能够支持以下完整场景。

**场景：使用 ChatGPT 与 Codex 协作阅读刷题网站。**

**步骤一：** 用户打开「刷题网站」工作空间，在左栏输入：

「我想从宏观角度理解这个项目。」

**步骤二：** 全局调度 Agent 建议让 Codex 扫描源码，生成项目结构摘要。

**步骤三：** 中栏出现一个待确认的 Codex 任务节点。

**步骤四：** 用户点击确认，任务进入执行状态。

**步骤五：** 右栏展示 Codex 的任务状态与执行信息。

**步骤六：** Codex 完成后，左栏显示结果摘要，中栏节点标记完成。

**步骤七：** 调度 Agent 建议结合扫描结果继续讨论架构。

**步骤八：** 用户在主群聊中继续与 ChatGPT 交流。

**步骤九：** 用户切换到消息泳道图，查看整个过程中不同主体之间的信息传递。

**步骤十：** 用户点击任意节点，能够查看对应任务的详细输入、输出和状态。

如果这一场景能够顺畅完成，说明 ContextFlow 的核心交互已经成立。

| 多个 Agent 同时执行时如何突出关键进展 | 待设计                   |
| 用户能否在图上直接创建任务            | 待讨论                   |
| 调度 Agent 是否可以主动提出建议       | 倾向支持，但需要控制打扰 |
| 如何衡量认知负载是否降低              | 待设计验证方法           |

## 12. 当前设计结论

ContextFlow v0.1 的核心界面确定为：

**可折叠三栏布局 + 多主体群聊 + 双视图协作画布 + 节点详情。**

其中：

**左栏负责交流，中栏负责理解全局，右栏负责深入细节。**

全局调度 Agent 与用户共同规划任务，但执行权仍由用户掌握。

流程图同时展示已发生的工作和未来计划；泳道图展示不同 Agent 之间的实际消息传递。

整个系统以减少无效协调负担为目标，而不是单纯增加自动化程度。

我们就用你现在真实存在的需求来设计一个完整场景：

# ContextFlow 场景 01：与 ChatGPT、Codex 协作阅读刷题网站

**场景目标：** 你希望从宏观上理解刷题网站的架构，并进一步判断哪些部分值得深入研究。

- **你：** 提出目标、讨论问题、确认任务。
- **ChatGPT：** 你的 AI 秘书，负责与你讨论、规划任务、解释结果。
- **Codex：** 执行者，负责直接读取本地源码、收集证据。

整个过程分为七个阶段。我会重点描述**你实际看到什么、需要做什么，以及三个界面如何变化**。

# 一、消息队列：保护正在进行的对话

你的想法是：

当 Codex 完成任务时，ContextFlow 应当自动把结果传递给 ChatGPT。

但是，如果你正在与 ChatGPT 讨论另一个问题，直接插入 Codex 的结果可能打断当前思路。

所以我们需要一个**独立于 ChatGPT 原生对话的待发送消息队列**。

## 1. 交互流程

```text
                Codex 完成任务
                      │
                      ▼
              ContextFlow 收到结果
                      │
                      ▼
               检查 ChatGPT 状态
                      │
             ┌────────┴────────┐
             ▼                 ▼
        当前适合接收       当前正在对话
             │                 │
             ▼                 ▼
       自动发送结果       加入待发送队列
             │                 │
             ▼                 ▼
       ChatGPT 继续分析    提示用户有新消息
                               │
                               ▼
                         用户审阅、确认
                               │
                               ▼
                         发送给 ChatGPT
```

不过这里有一个细节需要明确。

**「ChatGPT 没有正在生成回复」不一定意味着「你没有正在进行的讨论」。**

例如：

你刚刚与 ChatGPT 讨论到一个关键问题，它已经回复完毕，但你还在思考下一句话。

这时候 Codex 的结果突然插入，仍然可能打断你的思路。

因此，我建议不要只用模型是否正在生成回复来判断。

可以设计三种消息接收模式：

| 模式     | 行为                             | 适用场景           |
| -------- | -------------------------------- | ------------------ |
| 智能模式 | 根据对话活动状态判断是否自动发送 | 日常使用           |
| 手动模式 | 所有外部结果进入队列，等待确认   | 专注学习、深入讨论 |
| 自动模式 | 在会话空闲且可安全发送时自动传递 | 连续执行任务       |

默认使用智能模式。

第一版的「智能」不需要依赖 LLM 判断你是否正在思考，可以先采用明确的交互状态规则。

例如：输入框有未发送内容、ChatGPT 正在生成、用户主动开启专注模式时，统一进入队列。

此外，队列里的消息需要支持预览、删除、延后和手动发送。

**我认为消息队列不只是通信机制，更是用户注意力的缓冲区。**

# 四、我建议加入一个「专注控制」功能

这是根据你的需求自然推导出的设计。

**静默后台通知。**

- Codex、Claude Code 等任务继续执行；
- 任务完成后正常保存结果；
- 需要转发给 ChatGPT 的消息先进入队列；
- 不自动切换页面；
- 不弹出大型提示；
- 只保留一个待处理消息数量标识。

等你完成当前讨论，再统一处理后台结果。

这能解决你之前提到的注意力被多个 Agent 持续打断的问题。

而且它比简单地把某个面板最大化更重要。

**最大化解决视觉空间问题，静默模式解决注意力中断问题。**

二者应该独立控制。

## 六、我想进一步确认一个细节

你刚才提出：

> 如果当前没有对话，直接发送给 ChatGPT 即可。

我想确认这里的「没有对话」具体指什么。

**A. ChatGPT 当前没有正在生成回复。**

只要 ChatGPT 回复完成，后台消息就可以自动发送。

**B. 用户当前没有积极参与对话。**

例如你正在输入、阅读或思考时，即使 ChatGPT 已经回复完成，也应该暂缓发送。

**C. 用户主动控制对话是否接受后台消息。**

例如一个「允许自动接收后台消息」开关。开启时自动传递，关闭时全部进入队列。

**我目前更倾向于 B + C 的组合。**

也就是系统根据交互状态判断是否适合插入消息，同时允许你随时通过开关覆盖自动判断。

这样既保留你希望的自动化体验，也能让你在需要专注思考时完全掌握主动权。
