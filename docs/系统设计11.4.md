# ContextFlow 系统概要设计（第一阶段）

**文档状态：** 阶段性设计记录
**记录日期：** 2026-11-04
**设计阶段：** 系统概要设计——架构边界与模块职责
**范围：** 本文记录已讨论并确认的架构原则，不涉及具体技术栈、数据库结构或接口实现。

## 1. 项目定位

ContextFlow 是一个面向人机协作的通用多 Agent 协作框架。

它旨在将 ChatGPT、Codex、Claude Code 等已有 Agent 作为可接入的工作单元，通过统一的任务管理、消息传递、权限控制和状态记录机制，实现多个 Agent 之间的协作。

ContextFlow 不负责重新实现已有 Agent 的智能能力，而是重点解决：

- 不同 Agent 之间的任务分配与协作。
- 任务执行过程中的状态管理与可靠性。
- Coordinator 对工作进展的持续监督与策略调整。
- 用户对任务授权和协作过程的控制。
- 协作历史、任务流程和执行状态的统一展示。

**核心定位：ContextFlow 是一个由确定性 Core 支撑、由智能 Agent 参与决策、由用户控制授权边界的协作系统。**

具体使用时，可以选择 ChatGPT 网页端作为 Coordinator，Codex 和 Claude Code 作为 Worker，但这些工具不应被硬编码为框架的固定组成部分。

## 2. 总体架构原则

### 2.1 Core 与 Agent 分离

Core 主要通过确定性代码实现，不以 LLM 作为任务状态管理和执行控制的基础。

Core 负责维护系统中的事实与状态，包括：

- 任务与工作流。
- 消息及待发送队列。
- 用户审批和授权状态。
- 任务依赖与执行调度。
- 执行结果及事件记录。
- Agent 角色绑定与接入管理。

Agent 负责需要语义理解、复杂推理、规划和专业执行的工作。

**基本原则：模型负责语义决策，Core 负责可靠地执行和记录已授权的行为。**

### 2.2 Agent 与 Role 分离

区分三个概念：

- **Agent：** 实际提供能力的工具或系统，例如 ChatGPT、Codex、Claude Code。
- **Role：** Agent 在协作过程中承担的职责，例如 Coordinator、Worker、Reviewer。
- **Adapter：** 用于连接具体 Agent、屏蔽工具差异的适配组件。

角色不与具体 Agent 永久绑定。

同一个角色可以由不同 Agent 承担，具体绑定由工作空间配置决定。

### 2.3 Core 是协作状态的权威来源

Core 负责维护和持久化协作过程中可观测、可记录的事实。

前端流程图、消息泳道图和任务详情均应从 Core 的数据中派生，不应分别维护独立且可能冲突的状态。

Core 的完整性指其能够掌握自身负责的协作状态，不意味着能够获取外部 Agent 的全部内部信息或隐藏推理过程。

### 2.4 前后端解耦

前端是 ContextFlow 的交互和可视化层，而不是任务执行状态的唯一存储位置。

前端可以提供：

- 统一消息流。
- 任务流程图。
- 消息时序或泳道图。
- 执行详情与日志。
- 审批和消息队列操作。
- 可调整的多面板布局。

前端关闭后，Core 应仍然能够维护协作状态，并在运行环境及 Adapter 能力允许的情况下继续后台执行。

需要用户审批的操作可以保持等待状态，直到用户通过可用的交互入口作出决定。

## 3. 核心模块职责

### 3.1 ContextFlow Core

Core 是系统的协调执行基础设施。

主要职责：

1. 管理任务、执行状态和依赖关系。
2. 接收、保存和路由消息。
3. 管理用户审批及执行权限。
4. 按照已授权的计划调度任务。
5. 记录执行事件、结果及异常。
6. 管理 Coordinator 监督检查点。
7. 维护 Agent 与角色之间的绑定关系。
8. 向前端及 Agent 提供必要的工作状态。

Core 不负责直接判断复杂项目的技术方案是否合理，也不应自行作出超出用户授权范围的决策。

### 3.2 Coordinator Agent

Coordinator 是与用户直接协作的主要智能角色。

在当前个人使用配置中，优先考虑由 ChatGPT 网页端承担。

主要职责：

1. 理解用户目标和需求。
2. 制定任务计划与执行策略。
3. 提出任务分配建议。
4. 接收 Worker 的执行结果与状态反馈。
5. 在监督检查点评估工作进展。
6. 判断是否需要继续、等待、调整策略或请求用户介入。
7. 根据新信息持续更新对当前工作的理解。

**Coordinator 是持续参与协作的监督者，而不只是任务开始前的规划者。**

它可以提出新的执行策略，但不能绕过用户授权机制。

### 3.3 Worker Agent

Worker 是执行具体任务的 Agent。

例如：

- Codex 负责代码阅读、分析、修改或测试。
- Claude Code 负责独立审查或其他开发任务。
- 其他 Agent 负责搜索、资料整理或专业工作。

Worker 在分配的任务和权限范围内自主完成工作，并通过 Adapter 返回可观测的执行状态和结果。

### 3.4 Agent Adapter

Adapter 负责隔离具体 Agent 的接入差异。

主要职责包括：

- 将统一任务转换为具体 Agent 可接受的输入。
- 建立和维护与 Agent 的交互。
- 接收 Agent 的输出、状态及错误。
- 将具体工具的结果转换为 Core 可以处理的统一事件。
- 向 Core 声明或提供实际支持的能力。

Adapter 不应自行决定跨 Agent 工作流、用户审批策略或全局任务调度规则。

不同 Agent 的能力可能不同，不应假设所有 Agent 都支持流式输出、取消任务、主动消息接收或后台运行。

### 3.5 可选辅助智能服务

Core 可以调用辅助 LLM，但辅助模型不是第二个全局 Coordinator。

潜在用途包括：

- 从自然语言中提取结构化任务草案。
- 提取执行结果摘要。
- 对消息进行语义分类。
- 辅助识别任务建议和相关上下文。

辅助智能服务只提供语义处理结果，不直接拥有用户授权权力。

是否在第一版引入辅助 LLM、采用什么模型以及如何调用，尚未确定。

### 3.6 前端交互层

前端负责呈现 Core 中的协作信息，并向 Core 提交用户操作。

前端不应独立决定任务是否已获批准、是否已经执行成功或消息是否已经送达。

用户不必通过 ContextFlow 前端发起全部对话。例如，用户可以直接在 ChatGPT 网页端与 Coordinator 交流，再通过相应 Adapter 将可获得的交互信息接入 Core。

## 4. 任务执行与智能监督机制

### 4.1 确定性执行与智能监督并存

ContextFlow 不采用简单的「Coordinator 生成计划，Core 一次性执行到底」模式。

系统应当支持：

1. Coordinator 提出计划。
2. 用户批准相应执行范围。
3. Core 按照授权与依赖关系推进任务。
4. Worker 返回执行结果或状态。
5. 在配置的监督检查点，Coordinator 获得反馈并评估。
6. 根据评估结果继续执行、等待、调整策略或请求用户介入。

这一过程形成持续反馈的协作闭环。

### 4.2 可配置的监督检查点

**已确认：系统支持可配置的 Coordinator 监督检查点，不强制每个任务完成后都调用 LLM。**

不同任务可以采用不同监督策略。

例如：

- 简单、低风险的已授权任务，可以在完成后自动推进后续步骤。
- 关键分析任务完成后，可以暂停依赖任务，等待 Coordinator 评估。
- 任务失败、出现重要异常或执行结果与预期不符时，可以触发监督。
- 对于长期运行任务，可以根据实际需要进行状态检查。

监督结果不一定产生新的任务。

Coordinator 可以仅确认：

- 当前状态正常，继续执行。
- 当前状态正常，继续等待。
- 当前信息不足，需要进一步观察。
- 当前策略需要调整。
- 当前情况需要用户介入。

### 4.3 监督与审批分离

监督检查点和用户审批检查点是两种不同机制。

**Coordinator 监督：** 判断当前工作是否合理、是否应继续以及是否需要改变策略。

**用户审批：** 决定某项操作是否获得执行授权。

Coordinator 可以在既有授权范围内建议继续执行，但不能自行扩大任务权限。

例如，用户仅批准只读代码分析时，Coordinator 不能未经确认就要求 Worker 修改代码。

### 4.4 监督反馈与消息队列的关系

Worker 完成任务后，Core 可以立即记录完成事件和执行结果。

但向 Coordinator 传递反馈时，应考虑用户当前的交互状态与注意力策略。

如果用户正在专注讨论，且当前配置要求避免打断，反馈可以进入待发送队列。

任务完成和结果送达是两个独立状态。

如果监督检查点要求先完成评估才能继续，则相关后续任务应等待监督完成。

**需要监督不等于必须立即打断用户。**

## 5. 消息与状态管理原则

### 5.1 消息由 Core 统一管理

消息应具有明确的来源和目标。

例如：

- 用户发送给 Coordinator 的消息。
- Coordinator 提交的任务建议。
- Worker 返回给 Coordinator 的执行结果。
- Core 产生的系统状态通知。

统一消息流是展示方式，不意味着所有消息都会广播给所有 Agent。

### 5.2 区分任务状态与消息状态

任务完成不代表结果已经交给 Coordinator。

例如：

- Task T01：Completed。
- Message M08：Queued，等待发送给 Coordinator。

Core 应分别维护两者的状态。

### 5.3 区分消息发送与成功送达

Adapter 接收到发送请求，不代表目标 Agent 已成功收到消息。

消息传递机制应考虑：

- 发送失败。
- 送达状态未知。
- 重复发送。
- 外部会话不可用。
- 用户手动延迟消息。

具体消息状态机和可靠性策略将在详细设计阶段确定。

## 6. 架构验证场景

本阶段采用「分析真实 Web 项目的数据库可靠性」作为参考场景。

### 场景 A：任务规划与执行

1. 用户与 ChatGPT 讨论数据库可靠性问题。
2. ChatGPT 建议让 Codex 进行只读代码分析。
3. 系统将建议转换为任务草案。
4. Core 保存草案。
5. 用户确认执行。
6. Core 通过 Codex Adapter 分发任务。
7. Codex 执行并返回结果。
8. Core 记录执行状态与结果。

验证重点：Coordinator 负责规划，Core 负责执行状态和授权，Adapter 负责具体工具通信。

### 场景 B：持续对话与后台执行

1. Codex 在后台执行任务。
2. 用户继续与 ChatGPT 讨论其他技术问题。
3. Codex 完成任务。
4. Core 保存结果。
5. 结果根据注意力策略进入待发送队列。
6. 用户在适当时机将结果交给 Coordinator。
7. Coordinator 评估结果并提出下一步建议。

验证重点：后台执行、用户对话和 Coordinator 监督相互协作，但不应无条件互相打断。

### 场景 C：可配置监督检查点

1. 用户批准包含多个任务的计划。
2. Core 自动推进无需监督的任务。
3. 某个关键任务完成。
4. Core 在监督检查点等待 Coordinator 评估。
5. Coordinator 可以确认继续，也可以提出策略调整。
6. Core 根据监督结论和已有授权决定后续执行。

验证重点：确定性调度与智能监督并存。

### 场景 D：前端关闭与状态恢复

1. 用户关闭 ContextFlow 前端。
2. Core 继续维护后台任务及消息状态。
3. Worker 在运行环境允许的情况下继续执行。
4. 用户重新打开前端。
5. 前端从 Core 获取当前任务、消息和审批状态。

验证重点：前端不是状态的权威来源。

### 场景 E：Coordinator 替换

1. 当前 Coordinator 为 ChatGPT。
2. 用户将 Coordinator 角色绑定改为另一个 Agent。
3. Core 的任务管理、审批和调度机制保持不变。
4. 新 Coordinator 根据 Core 提供的工作状态和必要上下文继续协作。

验证重点：角色与具体 Agent 解耦。

需要注意，角色可替换不代表不同 Agent 的私有记忆、上下文和推理能力可以无损迁移。

## 10. 阶段性总结

ContextFlow 当前形成的总体架构思想是：

**Core 管理事实与执行，Coordinator 管理理解与策略，Worker 完成具体工作，用户掌握授权边界，Adapter 隔离工具差异，前端提供可替换的交互与展示。**

系统允许 Coordinator 持续监督工作进展，但不要求每个任务都经过 LLM 判断。

系统允许 Core 自动推进已授权任务，但不能让智能 Agent 绕过用户授权。

这一架构希望同时实现三个目标：

- **智能性：** 充分利用现有高能力 Agent 的理解、规划与执行能力。
- **可靠性：** 使用确定性机制管理任务、状态、消息和权限。
- **通用性：** 通过角色与适配器解耦，避免系统依赖特定 Agent 或前端界面。

**当前阶段结论：概要架构的主要职责边界已经明确，可以进入核心领域模型设计。**

ContextFlow 采用三级全局协作权限模型：完全人工确认、自动通信、完全自主协作。权限等级统一作用于所有 Agent 协作流程，并采用执行不中断、后续操作按新策略生效的切换机制。

## 三档全局协作权限

| 权限等级              | Agent 间通信       | 阶段性汇报与决策           |
| --------------------- | ------------------ | -------------------------- |
| Level 1：完全人工确认 | 每次都询问你       | 每次都询问你               |
| Level 2：自动通信     | 自动传递，无需确认 | 需要你确认                 |
| Level 3：完全自主协作 | 自动传递，无需确认 | Coordinator 自主判断和推进 |

## 明确三者的职责

| 组件        | 职责                                         |
| ----------- | -------------------------------------------- |
| Worker      | 执行任务、产生结果、向其他 Agent 发送消息    |
| Core        | 管理消息队列、权限检查、消息投递、状态记录   |
| Coordinator | 评价工作成果、监督进度、调整策略、提出新任务 |

这里我建议暂时把它理解为两个调度域，而不是马上引入一套递归的多层 Agent 框架。

|                           | 全局调度                     | Worker 内部调度                    |
| ------------------------- | ---------------------------- | ---------------------------------- |
| 管理对象                  | Slot、Task、跨 Worker 依赖   | 子 Agent、内部步骤、模型调用       |
| 决策依据                  | 工作目标、阶段结果、用户反馈 | 能力、额度、成本、上下文、失败情况 |
| 决策主体                  | Coordinator                  | Worker 自身                        |
| Core 的职责               | 记录状态、执行授权与调度规则 | 提供必要的运行与资源约束           |
| 是否需要 Coordinator 介入 | 阶段评价或策略变化时         | 正常情况下不需要                   |

## 现在开始第一轮推演：从用户需求到工作流创建

假设全局权限为 Level 2：自动通信，阶段性决策需要用户确认。

事件 01

用户提交需求

用户希望检查异常处理，不允许修改代码。

User

Coordinator

Coordinator

提出阶段规划

Core

保存规划草案，等待确认

这里我提出一个初步方案：

1. 用户的原始需求由 Core 保存，作为 Workspace 的目标和约束。
2. Coordinator 根据需求提出 Slot 和 Task 的规划草案。
3. Core 记录草案，但尚不启动 Task。
4. 用户确认后，Core 将草案转为正式工作流并启动第一个 Slot。

但这暴露出一个值得讨论的问题：

Coordinator 是否必须在一开始就规划所有 Slot 和 Task？

我认为不应该。

因为 Coordinator 还没读过项目代码，无法准确判断后续需要哪些具体任务。过早制定完整任务清单，容易产生大量无意义的计划。

我更倾向于：

- Coordinator 可以提出初步的阶段规划；
- 只详细定义当前即将执行的 Task；
- 后续 Slot 可以先保留目标，等前一阶段完成后再细化；
- 工作过程中允许新增、替代 Slot，而不是要求最初的规划永远正确。

Coordinator 可以提前规划阶段（Slot），但只需要为当前阶段创建具体 Task。后续阶段根据实际成果逐步细化。

Core 在这一阶段执行以下确定性操作：

1. 将已确认的 Slot 草案转为正式 Slot。
2. 创建当前阶段的 Task T01，并绑定执行主体 Codex。
3. 检查当前全局权限及 Task 的操作约束。
4. 将 T01 提交给对应 Agent Adapter。
5. 记录 Task 进入 `Running` 状态。

此后，Codex 可以自行组织内部执行，Core 不需要介入它的每个步骤。

假设你和 Coordinator 已经充分讨论，明确了 T01 的要求，并批准执行。

Codex 正常完成 T01，Core 收到了执行结果。

按照我们已经确认的规则：

1. T01 进入 `Succeeded`，执行生命周期结束。
2. Core 保存结果、日志及相关消息。
3. Core 根据预设监督检查点，将结果提供给 Coordinator。
4. Coordinator 评价成果，并判断是否需要与你继续讨论。

ContextFlow 使用统一的协作时间线展示用户、Coordinator、Agent 和系统产生的信息。时间线是记录与观察界面，不代表底层采用公开群聊通信。所有信息按实际接收目标定向投递；记录、投递、展示、聚焦与审批相互独立。Task 内部的协作记录默认折叠，不占据全局工作流视图。

## 区分当前计划与实际执行历史

我建议采用两个层次：

| 层次         | 内容                                    | 是否需要保留历史                 |
| ------------ | --------------------------------------- | -------------------------------- |
| 当前任务列表 | 计划中的 Slot、待执行 Task、执行顺序    | 可以直接更新，不必保留每一版计划 |
| 实际执行记录 | 已启动或已结束的 Task、输出、通信和评价 | 应当保留，便于追溯               |

到这里，我认为我们可以先确定：

- 默认读取 Workspace Overview。
- 根据需要展开 Slot 和 Task。
- 原始历史完整记录，但不默认注入。
- Coordinator 负责语义取舍和摘要更新。
- Core 负责保存、索引和按层级提供信息。

## 在 Core 中引入统一的辅助 LLM 能力

我建议不把它设计成第二个 Agent，而是作为 Core 的一个内部服务。

它可以在不同环节承担不同的信息处理角色：

| 使用位置           | LLM 的职责                     | 不应做什么                 |
| ------------------ | ------------------------------ | -------------------------- |
| 自然语言指令入口   | 转换为结构化操作               | 自行决定工作流如何变化     |
| Task 结束后        | 提取执行结果、压缩报告         | 判断 Task 是否满足阶段目标 |
| Slot 结束后        | 汇总阶段成果与关键事实         | 自行决定是否进入下一阶段   |
| Workspace 概览更新 | 压缩各阶段信息，形成宏观上下文 | 擅自改变全局目标和约束     |
| 消息展示           | 整理长消息，生成便于阅读的摘要 | 改变原始消息含义           |
