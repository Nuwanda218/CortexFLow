# 工作流与协作视图

本页整理已讨论的流程与状态，**不提供自动执行 DSL 或未经讨论的状态机**。来源：[S01-A1](../00-audit/material-audit.md#s01-a1)、[S01-A4](../00-audit/material-audit.md#s01-a4)、[S01-B1](../00-audit/material-audit.md#s01-b1)、[S01-C4](../00-audit/material-audit.md#s01-c4)。

<a id="wf-loop"></a>
## 1. 核心协作闭环【FR-01、FR-03–FR-07、FR-24】

| 环节 | 输入 → 结果 | 权限 / 证据边界 |
| --- | --- | --- |
| 自然讨论 | 用户目标 → ChatGPT 正常回复与行动建议 | 普通对话不直接执行 |
| 结构化分析 | 自然建议 → 任务草案 | 触发时机 Q04；独立分析不等于执行授权 |
| 人工审阅 | 草案 → 确认、修改或拒绝 | 多步确认粒度 Q01；修改和拒绝不自动执行 |
| 确定性分发 | 已确认任务 → 指定执行工具 | 当前首个集成范围建议是一个 CLI Agent |
| 状态与结果收集 | 工具反馈 → 当前状态、摘要、详情 | 不在工具返回前编造结果 |
| 接收策略 | 待回传结果 → 发送或暂缓队列 | “任务已完成”不等于“已传给 ChatGPT” |
| 后续讨论 | 已收到结果 → 解释、建议或新草案 | 新的执行任务仍需确认；不默认自动连续调度 |

“迭代”可表示用户与调度者根据已有结果开始下一轮讨论或任务；材料不支持首版复杂循环控制。自然讨论与执行可在时间上重叠，不要求用户等工具运行结束才能继续输入。

<a id="wf-task"></a>
## 2. 任务状态【FR-05、FR-11、FR-22、FR-23】

原稿的状态与视觉表达来自 [S01-A4](../00-audit/material-audit.md#s01-a4)，L251–260。

| 状态 | 已讨论含义 | 候选视觉表达 |
| --- | --- | --- |
| 待确认 | 尚未获得执行授权的计划 | 虚线边框 |
| 等待执行 | 尚未开始执行 | 普通边框、弱化内容 |
| 正在执行 | 执行工具正在处理任务 | 强调边框、轻量动态状态 |
| 已完成 | 工具返回完成结果 | 完成标识 |
| 执行失败 | 工具报告失败 | 错误标识 |
| 已取消 | 任务取消 | 弱化或划线 |

示例把“确认”到“运行”画成连续步骤，但实际状态须依据工具反馈。等待状态的依赖满足、分发时机没有完整契约；本页不新增“已批准”“调度中”等强制状态。

暂停虽出现在控制列表，却不在状态表中；暂停 / 取消确认、恢复、失败依赖与重试机制见 Q08。不能补造失败后必然进入重试队列的流程。

<a id="wf-queue"></a>
## 3. 结果发送与队列【FR-07–FR-10、FR-18】

来源：[S01-C1](../00-audit/material-audit.md#s01-c1)、[S01-C2](../00-audit/material-audit.md#s01-c2)、[S01-C5](../00-audit/material-audit.md#s01-c5)。下列词语只是对已有行为的展示区分，不新增自动定时状态转换。

| 情形 | 已讨论 / 候选行为 | 尚未确定 |
| --- | --- | --- |
| 执行任务完成 | 收集结果、更新任务、让用户能查看摘要 / 详情 | 回传内容选择 Q07 |
| 明确允许且适合发送 | 可送入目标 ChatGPT 会话 | 能力 Q02；自动判据 Q03 |
| 用户主动暂缓或不宜插入 | 保持“待发送”，可有轻量提示 | 默认模式、忙闲判据 Q03、Q10 |
| 用户预览 | 显示待发内容、来源、任务、时间、接收者 | 入口位置 Q15 |
| 用户选择稍后 | 延后，仍未发送 | 自动恢复时间未讨论，不设置计时器 |
| 用户选择立即发送 | 尝试将选定内容送到目标会话 | 发送失败 / 重复发送处理 Q08 |
| 用户取消发送 | 不发送该待发项 | 历史保留与“删除”对象 Q07、Q15 |
| 目标收到消息 | 可区分已传递与尚未传递 | 如何获得可靠送达证据 Q02 |

原稿建议三种接收模式：智能（依据活动）、手动（全部进队列）、自动（安全空闲时发送），并建议默认智能。**三种模式与默认值均未批准**；“自动”也不是无视用户输入或工具生成状态的强行插入。

任务结果可在左栏展示，并同时保持队列待发送；两者并不矛盾。发送内容的形式见[上下文管理](context-management.md)，通知的呈现见界面设计。

<a id="wf-flow"></a>
## 4. 流程图【FR-11、FR-12】

- 节点表示具体工作步骤，候选字段为编号、执行主体、任务名、状态、简短摘要；主体可以是用户或调度者，不仅是执行工具。
- 流程图包含历史和未来计划。历史来自实际已发生的状态，计划明确显示待确认 / 等待。
- 连线表达顺序依赖、并行分支与结果汇合。展示关系不代表已实现多执行 Agent 并行调度（Q05）。
- 原稿场景又画入提出需求、回复和确认事件；普通聊天是否都进入此图见 Q11，不定死粒度。
- 复杂循环、条件表达式、自动脚本为首版不建议目标；拖拽与编辑能力见 Q13。

<a id="wf-swim"></a>
## 5. 消息泳道【FR-13、FR-15】

- 每个参与者拥有泳道，按时间顺序展示实际通信；消息有发送者、接收者、方向和摘要。
- 概览用短标签，点击在详情看时间、类型、正文、关联任务和传递状态。
- ContextFlow 自己承担确认与传递，可有系统泳道；默认隐藏、排障时显示是 AI 候选，不作为已定设计。
- 待发送项不显示为已成功抵达 ChatGPT；不为了展示“理想闭环”伪造通信历史。

泳道排列和系统泳道可见性待 Q14。全量日志不是必须都成为泳道消息，保存边界见 Q07。

<a id="wf-link"></a>
## 6. 两种视图与详情的关系【FR-14、FR-15；NFR-02、NFR-04】

[S01-A4](../00-audit/material-audit.md#s01-a4)，L329–348 要求共享工作状态。一项任务可关联提交、启动、阶段结果、完成、接收等多条消息；从任务可查消息，从消息可找任务。

流程图回答“如何组织推进”，泳道回答“谁何时向谁传了什么”。它们是同一协作事实的不同投影，不是两个独立的执行或历史系统。
